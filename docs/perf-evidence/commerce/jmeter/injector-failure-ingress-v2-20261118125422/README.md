## HTTP 分布

以下各格为 P50/P95/P99，单位 ms；所有 5,000 笔样本均保留，没有删除错误样本。

| 结果 | 数量 | elapsed | Connect | Latency |
|---|---:|---:|---:|---:|
| 200 | 100 | 30295/31640/36947 | 10/776/6969 | 30295/31640/36947 |
| 409 | 4749 | 187/59968/65032 | 29/59914/65004 | 185/59968/65032 |
| ConnectTimeoutException | 151 | 32577/37960/38595 | 32576/37960/38595 | 0/0/0 |

100 笔受理最终对应 100 单 PAID、100 份活跃购买权益、库存 0，无重复或未终结状态。4,749 笔为 SOLD_OUT；另外 151 笔是连接超时，不能当作售罄。HTTP 401 和 5xx 均为 0。

原报告的 `connectFailures=0` 漏掉 ConnectTimeoutException，已在统计代码中用失败测试复现并修正；本归档保留原报告原字节，其正确分类是 **连接超时 151、非超时连接拒绝/不可达 0**。连接超时是总连接失败和总超时的重叠子类，不相加为 302 个失败请求。

此无效跑次的描述性口径：sampler 启动速率 52.011/s；HTTP 完成吞吐 50.434/s；HTTP 200 吞吐 1.040/s；唯一 PAID 记录点 TPS 1.121。这些值不构成 5,000 人同步容量结论。

## 直接可证与尚不能确认的边界

- JMeter GC/安全点日志在 HTTP 窗口内记录多次同步延迟：Cleanup 50 次，进入安全点累计约 14.104 秒；G1CollectForAllocation 15 次，进入安全点累计约 2.402 秒、在安全点累计约 3.341 秒。进入安全点不是“所有线程均暂停”，不能把这些时间再与重叠等待重复相加。
- 服务器已匹配的 4,849 笔 HTTP 入口均为 0 SQL。售罄应用处理 P95 约 136 ms，但 sampler 到服务器 TCP 接收 P95 约 59.915 秒；成功受理应用处理 P95 约 1.151 秒，而服务器响应结束到 sampler 完成 P95 约 31.004 秒。最长等待大部分位于业务处理之外。
- 这能证明负载发射与完成观测不正常，不能把全部连接延迟精确分配给客户端调度或 Windows 监听队列。缺少双方抓包、ETW 接入队列与当时主机物理内存时间序列，不宣称已确定唯一 TCP 根因。服务端应用 GC 最大暂停约 31 ms，不能解释几十秒尾延迟。
- 另有独立的后台数据库耦合：发送确认更新购买请求行，与消费者请求行 X 锁竞争。已由真实行锁 RED/GREEN 和独立 JAR 小规模真实 MQ 修复验证，见[锁修复报告](../../ack-request-lock-fix-20261118.md)。本无效跑次不用于计算该修复的性能提升比例。
- 原报告 `drainAfterLastHttpSec=61.722` 是最终确认上界，包含 JMeter 结束及报告采集延迟。最后主事务提交返回在最后 HTTP 完成约 6.8 秒前；已有数据库/队列观测也在最后 HTTP 完成前确认 100 条请求、回执、发送记录全部终态。缓存最终状态已核对，但精确缓存任务排空时刻当时未采集。因此不能据该数字断言真实积压持续了 62 秒。

建议后续先验证发压端实际发射条件及 TCP 接入证据，必要时隔离发压资源；同时保留逐秒发射量、连接超时与主机资源观测。**本轮不实现这些建议，不再跑 5,000 人，也不放宽任何超时或同步门槛。**
