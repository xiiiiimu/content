# 购买容量测量与诊断记录，2026-11-17

本轮仅执行三个 8 线程、每人一次购买的 Windows smoke。活动 74–76 是新建的测试活动。未清空数据库、重跑历史轮次或执行任何 5,000 线程负载。原 limited、stock、paced 的归档及 Git 暂存区保留。

## 新测试契约

- `run-purchase-capacity.ps1` 只接受明确的种子元数据路径、独立 runId、未使用的活动、充足库存与一次一买家。超过 20 线程须显式设置 `AllowCapacityLoad`。已有 runId 目录拒绝覆盖。种子生成 `jm-c<campaign>-u<buyer>`，同一购买可重试，换活动不会复用键。历史两条 5k 编排亦改用确定的元数据输出和显式 runId。后续容量判断使用新入口，历史编排保留各自的报告格式。
- JTL 保存 `userId / effClientKey / reservationId`，关闭请求头、响应头、请求数据和响应体。带 token 的种子 CSV 与私有元数据留在忽略目录，脚本不再打印私有元数据。证据目录只保存关联键、HTTP 元数据、数值指标及去凭据的运行参数。
- 请求与 HTTP 200 QPS 使用 `[首个样本开始, 最后一个样本完成]` 的共同分母。`emitRate` 另用首末启动间隔。`formal*Qps` 单独显示 JMeter 进程窗口，包含 JVM 冷启动及退出，排除 seed、preflight 和 warmup。结算窗口 TPS 用同一正式窗口内 `paid_at_ms` 的唯一 PAID 订单。全程 TPS 用全部已确认 PAID 订单除以从正式开始至确认排空的墙钟。`paid_at_ms` 是事务内记录的支付时间，不是独立的数据库 COMMIT 时间戳。
- 只读一致性快照按 reservationId 双向关联 HTTP 200 与活动请求，校验买家、客户端键、订单号、活动、帖子、商家、价格、PAID 状态、唯一 ACTIVE PURCHASE 权益和消费回执。项目的支付属于模拟支付，PAID 是该契约下的支付凭据。未结算、跨活动或无法唯一关联均失败。结算延迟使用 `paid_at_ms - created_at_ms`。
- 新入口已有自动失败条件，包括 JMeter/JTL 或线程数异常、任意连接错误或 HTTP 5xx、首购 HTTP 200 不齐、逐项对账差异、排空超时，以及实际滚动一秒启动峰值超过设定速率。压力阶段的实时人工停发条件另见下文。保留失败运行目录。

运行产物在 `target/purchase-capacity-smoke-*`，其中 `manifest.json` 绑定活动与运行配置，`observations.ndjson` 保存连续观测，子目录保存 JTL、窗口、报告和日志。Java 观测启动单独写入 `target/purchase-capacity-backend-d6db2df50d`。历史归档汇总和原始样本均未重写。

## 观测覆盖与判断

| 层 | 已实采 | 当前边界 |
| --- | --- | --- |
| 发压 | JTL 按实际启动时间计开始量，按完成时间计连接失败及收到 HTTP 响应量。补充滚动一秒启动峰值。 | 无服务端访问日志，历史 710 条拒绝无法逐请求跨层联接。 |
| Windows TCP | 本地 28080 的 `LISTENING / ESTABLISHED / TIME_WAIT` 等状态，快速采集用 `netstat`，首轮也取得系统级 TCP 计数。 | 系统计数混入其他连接。端口状态不包含监听队列占用、溢出计数或准确的 SYN 丢弃点。 |
| Tomcat | current/busy/max 线程、当前与最大连接数、进入应用过滤器后的 HTTP 在途量。活动 75 的忙线程峰值 4、连接数峰值 6。 | 尚无独立 accept/executor 队列深度和入队等待。JTL `Connect` 与 Servlet 指标不能相减得到精确等待。 |
| JVM / Hikari | Heap、GC pause 数量与时长、进程 CPU、线程状态，以及活跃连接、挂起等待、获取耗时和超时计数。活动 75 中活跃连接峰值 3，挂起和超时均为 0。 | 瞬时采样会漏过短峰值，探针 HTTP 请求也占用 Tomcat。不可将观测连接和线程全部归给购买流量。 |
| MQ / 结算 | 按活动计 MQ 已标记发送、PROCESSING、SUCCEEDED 和耐久消费回执，计数差分可得有效结算速率，并与逐条结算延迟对照。活动 75 从 8 已标记发送、5 PROCESSING、3 回执推进至 8 回执且排空，结算 P95 为 2.302 s。 | 回执速率不含重复投递，尚缺 Broker 实际消费、重试、队列 lag 和分段等待。 |
| MySQL | `data_lock_waits` 表级样本、活动行 `SELECT … FOR UPDATE` 的语句摘要累计次数及时间、应用账号事务累计次数及时间。活动 75 采到 `material_sale_campaigns` 上 **6 条等待关系**，锁语句摘要增加 8 次、累计约 2.78 s。 | 等待关系不是 6 条独立购买。摘要包含语句执行耗时，不能拆出精确锁等待；账号事务计数涵盖其他后台工作。尚无法直接测量每个 reservation 的事务持锁区间。 |

改为并行获取 JVM/Tomcat 与 TCP 状态并合并 MySQL 查询后，活动 75 共取得 22 个观测点，采样间隔中位数 2.103 s、最大 3.411 s。观测器记录每次采集起止，超过目标周期时不并发堆积额外批次。

**连接层判断。** 历史 paced 的 710 条均为 TCP 建连拒绝，且没有读超时或 5xx。最可能丢在 Windows 监听/连接接入至 Tomcat 接收前的路径。活动 75 复现了发压端请求集中发起，说明平均速率掩盖短峰值。没有历史同时刻的队列证据，尚不能确认具体是 Windows backlog、Tomcat 接收队列、短时监听不可用还是本机资源争用。下一步对齐独立发压端的连接结果、服务端监听与访问事件，并采集高峰 TCP 原生计数；先控制实测速率，再调整服务端参数。

**结算层判断。** 历史 paced 的 3,147 条 PROCESSING 与 179 s 排空说明接受速率超出了结算阶段的供给。活动 75 的实际锁等待证明活动表存在阻塞。本代码在同一事务中对活动 `FOR UPDATE`，然后执行校验、库存计数、订单、权益及回执写入，同一活动的并行 Worker 会竞争同一行。仍需通过固定速率、同一活动与多活动对照，测量锁等待、事务持续时间与 MQ lag 随负载变化的关系，才能量化它对历史积压的贡献。

## 下轮阶梯与停止条件

先修正冷启动的集中发起。候选方案是使用非购买请求预热 HTTP 客户端，或者将首个购买请求单独作为预热同步点，其余请求在 JVM 已就绪后开始正式分发。需先在 8–20 单验证实际 JTL 滚动一秒分布，再进入阶梯。若相同时间窗口反复超额，改用能独立调度请求起点的发压器或将发压端搬到另一台机器。

| 阶梯 | 累计首购买家与目标发起上限 | 判定目的 |
| --- | --- | --- |
| 0 | 20 单，2/s | 验证关联键、实际最多 2/s、监控与排空。 |
| 1 | 150 单，5/s | 对照同机/独立发压，检查 TCP 错误和结算基线。 |
| 2 | 600 单，10/s | 保持约 60 秒，测同活动结算是否追上流入。 |
| 3 | 900 单，15/s | 仅前两阶通过后进行。同活动与多活动各跑一组，比较锁和积压。 |
| 4 | 1,200 单，20/s | 仅 15/s 稳定、锁与队列可解释后进行，逐步提高实际在途量。 |

每阶使用独立活动、相同应用配置，前一阶完成排空与对账后再升级。这里的买家数是累计样本目标。并发以 JTL 活跃线程峰值及 Tomcat/应用在途实测汇报。建议每阶至少做两次同条件复现，将 5,000 留待独立授权和前序通过。

建议停止条件：首个连接拒绝、5xx、健康状态丢失、不可解释的关联缺失或 JTL 速率越界时终止本阶升级。连续 10 秒 Hikari 等待大于零或 Tomcat 忙线程超过配置 85%，以及 PROCESSING 连续三个 10 秒区间净增长且超过该阶 10 秒的到达量时，停止继续发放并保留排空证据。实时停发目前需操作员执行。脚本对 JTL 错误和对账做运行后硬门槛。

建议通过标准：实际请求速率达到目标的 90% 以上且滚动一秒不越界（以稳定段计）；全量实际首购 HTTP 200、零连接拒绝、零 5xx/超时、零跨活动重放、逐项对账零差异；正式发放结束后 30 秒内排空，稳定段后半程结算速率至少为实际流入的 95%；建议 HTTP P95 ≤2 s、P99 ≤5 s，结算 P95 ≤5 s，并记录判定窗口及探针缺口。这些是下轮的试验门槛，尚无生产 SLO 或容量结论。
