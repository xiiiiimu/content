## 已实现的保守改动

- `SaleService.purchase` 保留按用户和客户端键的持久化幂等查询、MySQL 活动状态查询及权威 `visibility.read`。Redis 活动状态并非授权或幂等的权威。异步首购在确认请求 INSERT 提交后返回确定的 `PROCESSING` 视图，省去一次读回。同步路径仍读最终结果。并发请求用不同客户端键但命中同一个 Redis 预留时，重复键处理可用预留 ID 读取同一活动、同一买家的记录。
- `settleBody` 在获取活动锁前用一个存在性查询替代订单整行和权益列表两次读取。账户与素材的决策行 upsert 已持有该行排他锁，去掉同事务重复读锁；退款和抽奖发奖仍经同一账户决策锁。动态黑名单检查仍在原位置，关闭、时间窗及库存验证沿用原序列。活动行仍 `FOR UPDATE`，以保持原关闭线性化与错误优先级。条件 UPDATE 也会把活动行锁持有至事务结束，当前未用它替换。
- V18 对新活动持久化固定素材版本。老活动列为空时走原默认版本读取。新活动不再为每笔结算读取素材资料。权益、请求状态和消费回执的写入异常会回滚整笔本地事务，包括活动库存和订单。支付契约仍是原有模拟支付。

查询条数及持锁范围可以从代码检查。活动锁前的所有权读取、固定版本减少的锁内读仅代表路径缩短。没有活动锁保持时间的同口径实测，因此未宣称时长或性能改善比例。

## 业务契约待确认

原有退款路径支持先买后中奖，再以 `GIVEAWAY_AUTO` 自动退款。现有黑名单测试还要求 Redis 预占之后新增黑名单可拒绝未结算订单。需要明确新活动的抽奖封口范围，以及活动期黑名单的新增和撤销是否能改变该活动资格。已提请确认的兼容方案是新活动开卖前完成本帖抽奖，开卖后不新增本帖抽奖，旧活动保留中奖自动退款。开卖快照冻结，同时保留运行期新增黑名单拦截未结算请求。当前没有改动抽奖、退款或黑名单的现有行为，也没有预先用 Redis 的名单结果代替权威规则。

## 速率校准与容量门槛

启动顺序的修复先让已计入对账的第一笔 HTTP 请求完成客户端初始化，再按间隔发放其余许可。许可留 4% 调度余量，JTL 仍对实际滚动一秒应用原配置上限。超过上限、稳定到达率低于目标 90%，或末条 HTTP 完成后超过 30 秒才确认排空，都会使容量入口失败。第一笔安全计入总量和排空，只有稳定到达率排除第一次冷启动间隔。没有延长请求超时或降低对账门槛。

两次未通过尝试保留。`preopt-cal-8b0b3306` 在首样本后卡住并终止该测试 JVM。`preopt-cal-b719d36a` 的 12 笔都完成，但滚动一秒有 3 次启动，速率门槛拒绝。调整间隔后的 `preopt-cal-aa964ec3` 有 12/12 HTTP 200、12/12 PAID、零连接错误及逐项差异，滚动一秒峰值 2，稳定段 1.870 次/秒，末条 HTTP 完成后 5.526 秒确认排空。该轮只校准旧实现的小样本行为。
