# 抢购入口 POST 的 QPS 上限：售罄路径（2026-11-20）

只测入口 `POST /api/sale-campaigns/{id}/purchase` 的 QPS，不测落单吞吐。没有修改业务代码和中间件配置；后端用现有 V26 JAR `content-v26-6924c4880b0d.jar`。

**后端、中间件（Docker）和发压机（k6）在同一台笔记本上，所有数字都是单机上限，不代表分布式部署的能力。**

受理路径（库存充足，100 → 800/s）按要求等确认后再跑，本报告不含。

## 1. 结论

- **售罄路径：阶梯 200 → 3000/s 每一级都有效且没有触发拐点。可持续入口 QPS ≥ 3000/s**（3000/s 那一级实际 2989.6/s，达到目标的 99.65%；P99 45 ms；0 错误）。上限没有测到，因为阶梯在 3000/s 就结束了。
- 3000/s 时已经接近整机 CPU 上限：整机 CPU P95 99%，有效频率从低负载时的约 2.9 GHz 降到约 1.76 GHz；P99 从 1500/s 时的 8 ms 升到 26 ms（2000/s）和 45 ms（3000/s），最大值 239 ms；VU 有 312 次（0.35%）没能按时发起请求。下一级最可能先触到的是**整机 CPU**（后端、Docker 虚拟机、k6 共用一台笔记本），而不是 Redis：Redis 单线程用了 0.55–0.67 个核，脚本服务端耗时每次约 0.1 ms，并且保持平稳。
- 是否继续加到 4000/5000/s，请确认。

## 3. 方法

- **发压工具：k6 v0.55.0 的 `constant-arrival-rate` 执行器**（`tools/k6-v0.55.0/`，官方 Windows 发行包，SHA-256 与官方校验列表一致）。选它的理由：
  - 它是真正的开放模型：按目标到达率准时发起请求，不依赖响应返回；发不出去时记为 `dropped_iterations`，"实际发射速率 ≥ 目标的 95%"可以直接判定。
  - JMeter 没有内置开放模型线程组（Arrivals 线程组需要插件）；Precise Throughput Timer 在响应变慢时会随之变慢；用 JVM 发压在 3000/s 下 CPU 成本也更高。
- **每级一次独立的 k6 运行**，30 秒，级间休息 15 秒；正式阶梯前先跑 100/s × 15 秒预热，不计入结论。
- **VU 数**：preAllocatedVUs 和 maxVUs 都设为 `ceil(到达率 × 50 ms × 3)`，下限 10，上限 600（预期响应时间 50 ms 取自此前良好环境下约 44 ms 的 P95）。各级分别为 30 / 75 / 150 / 225 / 300 / 450。请求超时 5 秒。
- **CPU 亲和性**：k6 绑定逻辑核 10–15（掩码 0xFC00，每级运行中都实测确认）；后端 JVM 绑定逻辑核 0–9（0x3FF，实测 1023）；Docker 虚拟机（MySQL、Redis、Broker）不绑定。哪些逻辑核是 P 核、哪些是 E 核没有核实。
- **售罄准备**：
  1. 新建活动 144（库存 4）；4 个卖方买家各下 1 单，等 4 单全部落单成功。
  2. 探测请求返回 `409 SOLD_OUT` 后才开始测量。
  3. 1000 个压测买家（与卖方不重复）按迭代号轮换，每个请求用新的 clientKey（`iq144-<级别>-<迭代号>`）。
  4. 买家用普通登录拿 Token（1004 人，28.7 秒），TTL 不变；每级开始前检查剩余有效期，本轮不需要刷新。
- **结果分类**：
  - 受理：200。
  - 售罄：409 且 `code=SOLD_OUT`。
  - 其他拒绝：401 / 403 / 404 / 其他 409 / 其他 4xx / 非 200 的 2xx。
  - 单列：503、其他 5xx、超时（k6 错误码 1050）、连接失败（无 HTTP 响应）。
  - 售罄路径上，除"售罄"外都算错误，包括意外受理。
- **轻量采集**：
  - 发压端：没有客户端 JFR、线程快照或逐请求输出，k6 只输出汇总。
  - 服务端：没有开启 JFR 录制；应用内耗时取自 Tomcat 访问日志的 `%D`（微秒，带缓冲写入，与 begin/end 毫秒差核对过）。
  - 按秒采样（`infra/jmeter/env_sampler.py`）：整机 CPU 和频率、各进程 CPU（后端、k6、vmmem、采样器自身）、`docker stats`、Redis 的 `commandstats`（脚本服务端耗时）、SLOWLOG、内存、Stream 长度和消费组 lag。采样器自身约占 0.2–0.3 个核。
- **有效性**：实际发射 ≥ 目标的 95%，且 k6 的 CPU P95 低于其 6 个核的 90%（5.4 核）。不满足的级别标为"发压机受限"，不计入结论。
- **拐点**：P99 > 200 ms，或错误率 > 0.1%，或实际到达率 < 95%（k6 未饱和时，说明是服务端响应慢占住了 VU）。可持续入口 QPS 取"从低到高连续没有拐点的最后一个有效级别"。

## 5. 拐点与瓶颈

- 阶梯内没有出现拐点；按规则，可持续入口 QPS 记为 **3000/s（实测 2989.6/s）**，这是阶梯的上限，不是测到的极限。
- 接近极限的迹象，都出现在 2000/s 以后：
  - P99 从 8 ms 升到 26 ms，再到 45 ms，最大值 239 ms；
  - 3000/s 时 VU 用满，有 312 次（0.35%）没能按时发起；
  - 整机 CPU P95 达到 96–99%，有效频率降到 1.76 GHz（低负载时约 2.9 GHz）。
- **最可能的瓶颈：整机 CPU。** 后端 JVM 用 3–3.6 个核，Docker 虚拟机用 3.3–6.5 个核，k6 用 2.3–2.7 个核，都在同一台笔记本上争用 CPU，而且 CPU 在高负载时降频。Redis 不是当前瓶颈：单线程只用了 0.55–0.67 个核，脚本服务端耗时 P95 约 0.13 ms，SLOWLOG 为空。
- 与上一轮（`campaign-lock-v26-20261120.md` §8）对比：当时受理路径在 60/s 下 Redis 预占脚本 P95 就到了 155 ms。本轮在售罄路径 3000/s 下脚本 P95 只有约 0.13 ms，SLOWLOG 为空。两轮的路径和负载都不同（受理路径会写 Stream、触发落单和缓存同步），不能直接说明上一轮的问题来自环境，只说明在当前环境下入口的 Redis 脚本本身不慢。

- 与 §3 相同：每级 30 秒，级间休息 15 秒，先 100/s 预热 15 秒，新活动（146），1000 个买家，每个请求一个新 clientKey，k6 绑定逻辑核 10–15，后端绑定逻辑核 0–9。

### 8.3 时间花在了哪里

- **应用内耗时很低，大部分时间花在应用之外。** 4000/s 时应用内 P99 只有 25 ms，客户端 P99 却是 346 ms；k6 的分项显示，这部分时间是 TCP 建连（P99 128 ms）和等待首字节（P99 296 ms）。
- **服务端同时在处理的请求最多只有 110–118 个**，远低于 Tomcat 线程数和 k6 的 VU 数，说明请求不是卡在应用线程上，而是在进入 Tomcat 之前排队：内核网络栈、NIO 轮询线程，以及 k6 自身的调度。三者都在争整机 CPU。
- **按秒看服务端吞吐**：
  - 3500/s 那一级，前 11 秒吞吐只有 800 → 2400 → 3500/s，并伴随大量新建连接；第 12–29 秒稳定在 3500/s，应用内 P99 为 6–25 ms。
  - 4000/s 全程基本稳定在 4000/s。
  - 5000/s 每秒在 3600–5900 之间波动，客户端 P50 已经升到 53 ms（应用内 P50 15 ms），这是稳态排队。

### 8.4 对照：大 VU 池会不会自己造成退化

- **为什么要做对照**：k6 的每个 VU 各用一条 TCP 连接，每级又是一个新的 k6 进程，所以 VU 池越大，每级开始时要新建的连接就越多。§4 的 3000/s（450 个 VU）建连 P99 为 0；本节 2000 个以上的 VU，建连 P99 为 128–559 ms。为了把“VU 池大小”和“到达率”分开，用同样的 VU 估算（预期 200 ms，上限 4000）补跑了 3000 和 3500：新后端、新活动 147，先 100/s 预热。

| 3500/s（2100 VU，紧接上一级，已预热） | 3500.0 | 100.0% | 0 | 221.1 / 460.1 | 41.8 | 121.4 | 98% | 4.24 |

- **结论 1**：直接从 100/s 跳到 3000/s 以上的那一级，都有一段约 10 秒的冷启动过程：吞吐慢慢爬升，后端 CPU 冲到 7.7 核，同时新建 2000 个左右的连接。这一级的 P99 会被拉到 1 秒左右，与目标是 3000 还是 3500 无关。所以 §8.2 中 3500/s 的数字主要反映冷启动，不是稳态。
- **结论 2（真实拐点）**：经过预热、没有冷启动干扰时：
  - 3000/s 在 §4 的逐级阶梯中通过（P99 45 ms）；
  - 3500/s 在对照中刚好越线（P99 221 ms，到达 100%，0 错误）；
  - 4000/s 的 P99 为 346 ms，5000/s 为 676 ms，越线越多。
- **拐点在 3000–3500/s 之间，可持续入口 QPS 仍为 3000/s。**
- **结论 3**：§4 中 3000/s 那一级有 312 次未发起，当时 450 个 VU 少于“到达率 × 最长迭代 240 ms”所需的约 720 个，存在 VU 不足的可能。本节加大 VU 池后，阶梯式的 3000/s 没有复测，所以那 312 次的原因“缺证据”。

### 8.5 拐点处的瓶颈资源

- **整机 CPU。** 3500/s 及以上时，整机 CPU P50 88–95%、P95 97–100%，有效频率只有 1.72–1.74 GHz（低负载时 2.7–2.9 GHz；`PercentofMaximumFrequency` 始终 80%）。
- 各进程分别用掉：后端 JVM 约 3.7–4.4 核（P95 最高 7.6），Docker 虚拟机约 3.9 核（P95 最高 6.8），k6 约 2.5–3.3 核（P95 4.3–4.8）。三者合计接近 16 个逻辑核在降频状态下的容量。
- 应用内耗时仍然很低（P99 25–30 ms），多出来的时间在建连和 Tomcat 之前的排队。
- **第二个即将到顶的资源是 Redis 单线程**：5000/s 时 Redis 容器 CPU P50 88%、P95 105%，已接近 1 个核。脚本每次的服务端耗时仍在约 0.1 ms，暂时还没有变慢。在这台笔记本上，再往上压，CPU 和 Redis 单线程会同时成为上限。
- **以上都是单机数字**：后端、中间件、发压机共用一台笔记本，k6 自身就用了 2.5–4.8 个核。

## 9. 受理路径：100 → 200 → 400/s，以及暂停落单的诊断

### 9.1 方法

- **工具与基本设置**：k6 开放模型；每级 20 秒，级间休息 15 秒；先 50/s × 10 秒预热（单独的活动，单独排空和对账，不计入结论）。VU = 到达率 × 200 ms × 3（上限 4000）。CPU 亲和性与售罄路径相同。后端为同一个 V26 JAR、档位 B（批量派发，并发 1），PID 45388。
- **活动与买家**：
  - 4000 个隔离买家（`formal-reuse.csv`），普通登录，用时 111 秒，Token 的有效期不变。本轮没有触发 Token 刷新。
  - 每一级都用全新的活动和素材，每个活动的库存 = 4000，足够、不会售罄。
  - 第 i 个请求发到第 `i % n` 个活动，买家取第 `floor(i / n)` 个，所以 **(买家, 素材) 不会重复**；k6 中还有越界计数（`pair_overflow`），全程为 0。
  - 活动编号：预热 151；100/s 为 152；200/s 为 153、154；200/s 暂停落单为 155、156；400/s 为 157、158、159。建活动共用 56 秒。
- **排空**：每级结束后轮询，直到同时满足：MySQL 中没有 PROCESSING 的请求、没有 HELD 的订单、Redis 中没有 PROCESSING 的预占、Stream 的 pending 和 lag 为 0、派发表和缓存同步任务都已完成。排空时间从发压窗口结束算起，**单独记录，不计入 QPS**。
- **逐笔对账**：k6 用 `--console-output` 为每个请求写一行记录（迭代号、活动、买家、状态码、reservationId；不含 Token；只在 `target/`）。每一笔都要满足下面的条件，任何一级对账失败就停止，不进入下一级：
  1. 每个 200 都能在 MySQL 找到同一个 reservationId，且买家、活动、clientKey 一致；
  2. 请求状态为 SUCCEEDED，对应订单为 PAID，有且仅有 1 条 ACTIVE 权益；
  3. 没有任何对不上 200 的多余记录；
  4. 每个活动的 `sold_count` = SUCCEEDED 请求数 = PAID 订单数 = 权益数，没有重复订单或重复权益；
  5. Redis 库存 = 库存上限 − 已售；Redis 中没有遗留 PROCESSING 的预占。
- **暂停落单的诊断**：在 200/s 级之后，用已有钩子 `POST /api/sale-debug/hold-settle {"arm":true}` 再跑一次 200/s：
  - 钩子让所有 settle 在入口处等待（最多 120 秒）；**桥接（Stream → MySQL）和 MQ 派发照常运行**。
  - 结束后立即解除，然后排空、对账。
  - 解除前查到：这两个活动 SUCCEEDED 为 0、PROCESSING 为 3268，证明这段时间确实没有落单。

证据：`docs/perf-evidence/commerce/jmeter/ingress-qps-accept-20261120-065943/`（`ingress-qps.json` 内含每级的排空和对账结果）；逐笔记录、排空过程、按秒原始采样在 `target/ingress-qps-20261120-060505/accept-20261120-065943/`。
