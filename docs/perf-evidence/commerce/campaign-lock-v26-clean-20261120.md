# V26 落单对照：干净环境重跑 B / 并发 2 / C（2026-11-20）

同一个 V26 JAR（`content-v26-6924c4880b0d.jar`，与 `campaign-lock-v26-20261120.md` §4 相同），在当前环境按同样的方法重跑三档。与上一轮受环境影响的 V26 三档、以及修复前（V25 及更早）的 B/C 对比。没有修改业务代码和中间件配置。

**后端、中间件、JMeter 都在同一台笔记本上，所有数字都是单机数字。**

## 1. 结论

- **环境恢复后，V26 三档全面好转。**
  - 全程成交 TPS：B 19.5、B2 28.0、C 28.3。受环境影响时为 7.1 / 10.0 / 11.0，修复前 B/C 为 10.0 / 10.3。
  - 请求到提交的 P95：151 / 104 / 83 秒，受环境影响时为 367 / 247 / 223 秒。
  - 排空时间：125 / 70 / 69 秒，受环境影响时为 355 / 228 / 211 秒。
  - HTTP P95 回到 14–15 ms（受环境影响时 196–244 ms，修复前 44–46 ms），到达率 59.9–60.0/s。
  - 三档的正确性、重放、孤儿引用检查全部通过，发送失败为 0。
- **上一轮 V26 的 HTTP 和 Redis 变慢是环境问题。**
  - 对比两轮环境：现在 WSL 上限已生效、Docker 内存 4.8 GiB，上一轮 7.6 GiB；负载下有效频率现在 1.8–2.2 GHz，上一轮约 1.3 GHz。
  - 同一个 JAR、同样的方法，HTTP P95 从 196–244 ms 降到 14–15 ms；Redis 服务端脚本 P95 从 3.9 ms 降到 0.33–0.36 ms；窗口内没有业务脚本进入 SLOWLOG。
  - 这回答了 `campaign-lock-v26-20261120.md` §5 和 §8 留下的问题。**用独立数据库跑 V25 对照已经没有必要。**
- **三档各自的瓶颈**（§4 详述）：
  - **B：发送。** 串行批量派发在窗口内只有 17.3 单/秒，派发待发峰值 2,526；落单很快，几乎没有活动行锁等待。
  - **B2：发送和落单提交同时到顶。** 派发 27.3 单/秒，TPS 已与 C 持平，活动行锁等待开始大量出现。
  - **C：落单提交（单活动热点行）。** 派发 48 单/秒，跟得上；消息转而积压在 Broker（峰值 1,719）；成交 TPS 停在约 28 单/秒，活动行锁等待 6,280 次。
  - **主机 CPU 不是首要瓶颈，但会放大提交耗时。** C 窗口内整机 CPU P50 78%、P95 98%，频率 1.84 GHz；落单提交 P50 34 ms，约为空闲时（16–17 ms）的 2 倍。全系统提交约 107 次/秒，远低于空闲时 307–353 次/秒的预算。
- **单活动上限**：本机负载下约 **28 单/秒**（B2、C 实测），持锁区间 P50 32 ms，对应约 31 单/秒。上一轮受环境影响时的估计是 11–18 单/秒；若提交耗时能回到空闲水平，理论上限约 55–60 单/秒。

## 2. 环境与方法

- **环境**：
  - 交流供电，高性能计划；`.wslconfig` 已生效，Docker 内存 4.80 GiB；资源关卡每档通过（`*-gate-start.json`）。
  - 后端绑定逻辑核 0–9（三档各自的 `*-backend-affinity.json` 都实测为 0x3FF）；JMeter 和 Docker 虚拟机不绑定。
- **方法**：与上一轮相同，脚本是 `run_dispatch_comparison.py --profiles B B2 C --skip-smoke`。
  - 每档：资源关卡、新后端、新活动、新 clientKey；4000 个隔离买家重新登录；60/s × 60 秒（开放模型 V23Pacer）；bridge 批量 20；20 个消费线程。
  - 每档结束后由 `run_v23_performance.py` 排空，然后逐笔对账：请求、订单、权益、Redis 预占和库存、孤儿引用、重放。任何一项不通过就停止，不进入下一档。
  - 三档参数：B = (batch, 20, 1)，B2 = (batch, 20, 2)，C = (batch, 20, 4)。
- **本轮唯一的方法改动**：`run_dispatch_comparison.py` 新增可选参数 `--backend-affinity`，默认不启用，原有行为不变。启用后在后端启动后设置亲和性，并写入公开证据。
- **按秒采集**：`env_sampler.py` 覆盖三档全程，采集整机 CPU 与频率、各进程 CPU、docker stats、Redis 脚本耗时、SLOWLOG、Stream 积压。
  - Broker 消费积压由原有的 lag 采样器提供，每 5 秒一次。
  - 采样器自身约占 0.2–0.3 个核。上一轮的 §4 没有这项采样，§8 有。
- **指标提取**：用同一份提取逻辑处理九档数据，该逻辑已整理为 `infra/jmeter/campaign_lock_digest.py`（附 `test_campaign_lock_digest.py`），提取结果是 `digest.json`。

证据：公开 `docs/perf-evidence/commerce/jmeter/campaign-lock-clean-20261120-073658/`（`B/`、`B2/`、`C/` 三档完整证据，`*-env-sample-report.json`，`digest.json`）；私有 `target/campaign-lock-clean-20261120-073658/`（按秒原始采样 `env/`、后端日志、买家数据）。

## 4. 瓶颈分析

| 档位 | 发送（派发） | 落单提交（单活动热点行） | 主机 CPU | 判定 |
|---|---|---|---|---|
| B (1 并发) | 窗口内 17.3 单/秒，低于到达率；派发 PENDING 峰值 2,526，窗口结束时 2,525 条未发 | 落单事务开始→主提交 P50 84 ms，活动行锁等待只有 17 次；Broker 积压 ≤ 7，消费端在空等 | 整机 P50 40%，后端 P50 0.9 核 | **发送** |
| B2 (2 并发) | 27.3 单/秒，PENDING 峰值 1,926，仍略低于到达率 | 活动行锁等待 4,913 次，事务开始→主提交 P50 552 ms；Broker 积压峰值 375 | 整机 P50 65%，频率 1.89 GHz | **发送和落单提交同时到顶**；TPS 已与 C 持平 |
| C (4 并发) | 窗口内 48.2 单/秒，超过到达率；PENDING 峰值 420，窗口结束 30 秒内全部发完 | 活动行锁等待 6,280 次，事务开始→主提交 P50 568 ms；Broker 积压峰值 1,719（消息在 Broker 排队等消费）；成交 28.3 单/秒 | 整机 P50 78% / P95 98%，频率 1.84 GHz | **落单提交**（单活动热点行） |

- **单活动上限的计算**：活动行上的 `tryIncrementSold` 到提交之间串行持锁，C 档持锁区间 P50 32 ms（P95 52 ms），对应约 31 单/秒；实测 B2 28.0、C 28.3。把派发从 2 并发加到 4 并发，成交 TPS 不再增加，多出来的派发能力只是把积压从 MySQL 派发表挪到了 Broker。
- **主机 CPU 的作用**：
  - 它不是直接瓶颈：全系统提交约 107 次/秒，只占空闲预算（307–353 次/秒）的约三分之一；后端 P50 只用了 1.7 核。
  - 但它放大了热点行的持锁时间：落单提交 P50 34 ms，约为空闲时（单连接同一行 16.5–17.5 ms）的 2 倍。负载下 MySQL 容器用了 1.3–1.9 个核，整机 P95 98%，频率降到 1.84 GHz，这些都会拉长每次提交。
  - 若提交耗时能回到空闲水平，单活动理论上限约 55–60 单/秒；在这台共用的笔记本上测不到。
- **请求→提交的 P95 仍有 83–151 秒**：到达率 60/s 是落单能力（约 28/s）的 2 倍以上，所以请求在 60 秒窗口内持续积压，P95 反映的是排队，不是单笔处理慢。若到达率不超过约 28/s，这个时间会大幅缩短；本轮没有测，**缺证据**。
- **上一轮的结论需要更正**：上一轮 §4.2 给出的单活动上限 11–18 单/秒是在环境受限下测到的，干净环境下约 28 单/秒。§5 记为“未解释”的 Redis 和提交变慢，现已确认是环境问题，见 §1。
