## 2. 实现说明

### R2：只读当前话题；索引；清理
- `emitSpikeIfNeeded` 改用 `topicNetSince(topic, since)`。它走主键前缀，EXPLAIN 为 `type=range key=PRIMARY rows=2`（144 万行的库）。原来是全表扫描，`rows=1,296,792`。
- **V27 只加时间开头的索引，不包含计数列**。这样点赞热路径上的 `net_events=net_events+1` 不需要维护这些二级索引。
  - 1 小时窗口：`type=range key=ix_bucket_start`
  - 清理 DELETE：`type=range key=ix_bucket_start`
  - **24 小时窗口**：优化器在这个库上选择了 PRIMARY 全扫描（`rows=1,448,448`），因为预置的 25 小时数据大约一半都落在窗口内。保留期 48 小时上线后，24 小时窗口本来就要读约一半的保留数据。这是读路径，不持有锁，规模被保留期限住。它的耗时**本轮没有测，缺证据**。
- **清理任务 `TopicRetention`**：
  - 保留期 `content.trending.retention-millis`，默认 48 h（最长窗口 24 h + 24 h 余量）。**小于 25 h 时启动直接失败**。
  - 每批 `content.trending.retention-batch` 行（默认 500），间隔 `content.trending.retention-interval-millis`（默认 10 分钟），在独立的守护线程上执行。`content.trending.retention-enabled=false` 可以关闭。
  - **对锁的影响**：
    - 每批是一个独立的 READ COMMITTED 短事务，按 `ORDER BY 时间 LIMIT n` 删除最旧的行，没有间隙锁，只锁住本批被删的行，持续一批的时间。
    - 在线写入只碰当前分钟的桶。取消赞只碰该赞自己的 ledger 行和那一分钟的桶。所以只有在“取消一个已经超过保留期的赞”时，才可能和清理争同一行，最多等一批。
    - 没有用默认的 REPEATABLE READ 自动提交，是为了避免表里没有新于 cutoff 的行时，next-key 锁锁到 supremum、挡住新插入。
  - 本次压测期间应用日志里没有清理相关的记录。清理只在删到行或失败时才打日志；历史桶最多 25 小时，按设计不会被删。**清理任务在压测期间是否实际执行过，没有直接证据**。
- **注意**：`rebuild(windowMillis)` 依赖 ledger，窗口大于保留期时会缺数据。目前调用方只用 1 小时，没有冲突。

### R1：话题来自帖子本身
- 先确认了数据来源：原来**帖子没有话题字段**，`/api/topics/{topic}/posts` 读的是 `topic_event_ledger`，而 ledger 里的话题就是客户端传的。按你的选择新增了 `posts.topic`，话题统计和话题页现在都从这一个字段取。
- `POST /api/posts` 可以带 `topic`。`PATCH /api/posts/{id}`：不带 `topic` 字段时保留原值；字符串表示设置；`null` 或空串表示清除。话题会去掉首尾空白，最长 128 字符，不能含控制字符，否则返回 400 `INVALID_TOPIC`。
- `InteractionService` 在互动事务内读取 `posts.topic`，每个请求多一次主键查询。客户端的 `topic` 参数仍然接受，但被忽略。**帖子没有话题时不写 ledger 和分钟桶**。
- **上线影响（需要你决定）**：
  1. 现有帖子的 `topic` 都是 NULL，上线后它们的互动不再进入话题统计。
  2. 话题页（`/api/topics/{topic}/posts`）上线后会立即变空，直到有帖子设置了话题。
  3. **前端还没有设置话题的入口**，本轮没有改前端，作者目前只能通过 API 设置。
  4. 素材帖的创建入口不接受话题，只能事后用 PATCH 设置。

### R8：只在状态翻转时计数
- 赞从无到有：写 ledger 行 `like:{post}:{user}`，当前分钟桶 +1。
- 赞从有到无（取消赞，或踩时顺带移除了已有的赞）：删除这条 ledger 行，并从**这个赞当初所在的那一分钟的桶**减 1（用 `GREATEST(...,0)` 兜底）。**不再写单独的 -1 事件**。
- 由此：每个（帖子, 用户）的 ledger 最多 1 行；赞/取消循环的净值回到 0，永远不会为负；取消一个很久以前的赞，不会扣减当前窗口。
- **语义变化**：
  - `active_interactions` 会和 `net_events` 一起撤回。取消赞不再算作一次活跃互动。这样分钟桶始终等于从 ledger 重建出来的结果。
  - 原来“踩时移除了赞，但赞的 +1 留在统计里”的问题也一并修掉了。
  - 取消赞不再走 serial 锁。
- **旧数据**：改动前写入的 `unlike:*` ledger 行会保留，直到保留期清理掉。改动前如果出现过“赞 → 取消 → 再赞”，ledger 中残留的那行赞会让再次点赞不加分（偏少，不会为负）。

### R9：已报过就跳过
- 检查话题刷新时，先查进程内记录：本小时这个话题已经报过，就直接返回，不拿 serial 锁、不扫描、不插入。
- 什么时候记为“已报过”：本事务的插入**提交之后**才记，所以回滚不会把窗口误记为已报过；或者插入撞上唯一键时立即记，说明别的事务、别的节点或者重启前已经插入过。只保留当前和上一个小时。
- **限制**：每个节点要通过一次重复插入才能得知某个窗口已报过。人工删除的风险行，在已经记住它的节点上，要到下一个小时才会重新上报。

## 4. 压测方法

- **应用**：改前/改后各自的 jar（`target/perf-r1-20261120-2222/{before,after}/app-*.jar`）。
  - 每个阶段都用**全新的独立库**（`content_perf_r1_before_222421` / `content_perf_r1_after_234551`），由 Flyway 从空库迁移。
  - Redis 用 db 7；端口 28180；`content.feed.enabled=true`，不启用 relay/pipeline。
  - 没有碰 `content` 库，也没有碰抢购数据。
  - JVM `-Xms1g -Xmx1g`；Hikari 用项目默认（最大 16 连接，`connectionTimeout` 5 s）。两次参数一致，**没有调大连接池或超时**。
- **数据**：1 个作者、4000 个关注者；每组运行都用新的帖子。
  - (a) 每组 100 个帖子，不带话题
  - (b)/(c) 每组 4 个帖子，话题 `r1b50`…`r1c200`。改前由客户端传 topic，改后写在 `posts.topic`，客户端仍然传但被忽略。
  - (c) 在 (b) 之后预置 1000 个话题 × 1440 分钟（61–1500 分钟前）的历史桶，共 144 万行。改后的保留期是 48 h，这些行不会被清理，对比是公平的。
- **负载**：k6 v0.55 `constant-arrival-rate`（开放模型），每档 60 s，`maxVUs` 400，单次请求超时 60 s。
  - 每个请求都是唯一的（用户, 帖子）组合，所以每次都是一次真实的状态翻转。
  - token 在 k6 中按测试密钥本地签名，密钥只放在 `target/`。
  - 每档开始前等 Hikari active/pending 都归零，并且先跑 20 rps 预热。
- **指标**：
  - k6 的 p50/p95/p99、状态码分类、`dropped_iterations`
  - MySQL 全局 `Innodb_row_lock_waits`/`_time` 的前后差值（库内没有其他负载）
  - Hikari：`hikaricp.connections.acquire` 计数和总时长的差值，以及每秒采样的 `hikaricp.connections.pending` 最大值
  - k6、应用和 Docker Desktop 上的 MySQL 跑在同一台机器上，没有开 JFR 或线程快照
- **工具**：`infra/perf/interactions/`（`like.k6.js`、`run-phase.sh`、`summarize.py`）。

## 6. 建议的下一步（等你决定）
1. **同一话题分钟桶的热点**（R1/R2 残余）：分钟桶拆成多个分片（`topic, bucket, shard`，读时求和）；或者事务内只写 ledger 或 outbox，后台按分钟合并到桶。验证方法：用本轮的 b/c 场景，看 100/200 rps 是否零错误。
2. **a200 的瓶颈拆分**：分别观察 `post_stats` 行锁和连接获取次数。可选方向：把 `visibility.read` 放进同一个连接或同一个事务，减少 3 次获取；或者先修 R3（计数改为增量更新）。
3. **上线前的数据决策**：现有帖子话题全为空，话题页上线即为空，前端也没有设置话题的入口（见 §2 R1）。另外，旧的 `unlike:*` ledger 行会等到 48 小时清理；要不要在上线时直接清空并重建，需要你决定。
4. **缺证据项**：24 小时热榜窗口在 48 小时保留数据下的读取耗时；清理任务在大量过期数据下的单批耗时，以及对在线写入的影响。
