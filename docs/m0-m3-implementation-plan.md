## M3 分发与迁移落地

- PUSH 事件由 Inbox 唯一键和 Task 的 event_id 唯一键约束，同一事务写入，提交后 ACK。PULL 事件在 Feed 消费者记录已按持久化模式判定无需扇出的结果，无需创建分发任务。发布事件若与任务数据冲突，进入对账而非静默跳过。
- 领取任务后记住 token，以数据库时间判定租约。按 follower_id 递增扫描，第一次领取时持久化 ID 上界，批次后推进游标用 state、token、有效租约条件更新。上界限制扫描范围，关注新加入和关系变化由 ADR-003 处理。Redis 部分失败不推进；Redis 全部成功后才提交进度。DEAD 任务告警并支持保留事件身份的人工重放。
- 读取按不可变 delivery_epoch/mode 和迁移覆盖范围选取来源。旧 PULL 保持权威拉取直到历史窗口退役或验证回填覆盖。旧 PUSH 依赖 inbox 时，Redis 故障后从主库按相同关注谓词、保留窗口和排序直接拉取。切换重复发生时，每段历史独立覆盖，禁止以最新模式覆盖所有历史。
- Redis 恢复阶段用权威读取，旧会话仅在可证明覆盖时延用原边界，否则返回 CURSOR_STALE。使用持久化恢复状态和 Redis 就绪标记识别索引未就绪；读缓存禁用淘汰，禁止未受控地删除单个活跃 inbox。恢复期间可在隔离键空间重建。没有完成并发写追平及覆盖验证时保持权威读取。首版若需重新启用 Redis，可采用受控维护窗口，暂停影响覆盖的发布、关系变更和分发写入，等待在途写结束并隔离旧 Worker，再重建、核验并切换 generation。无停机追平协议另行验收。
- Redis 丢失后已 DONE 的任务不会自然重投，因此恢复从权威帖子与当前关注代次计算。不能只扫未完成任务。检测失效、恢复标记和流量保护均需要故障注入。

M4–M7 按 ADR-004 扩展可见性与完整故障验收。保留互动、热点榜、媒体、M8 性能工程和 M9 TrendGuard。每阶段记录 commit、环境、测试日志和未通过项。没有实测数据时不给性能数字。

## 尚未解决的风险

- 权威降级的扫描成本和容量待测。需要定义过载拒绝阈值，并确认不可用与耗尽可区分。
- 关注回填在作者行锁内读取并落库，热点作者的锁竞争和索引成本待测。按固定锁顺序及有界回填实施。
- 单个 Redis 键被人工修改或部分丢失时，就绪标记本身不能证明索引完整。需要限制写权限、对账抽样和告警，验收其发现及恢复窗口。
- M2 的逻辑来源数量须受控；Pull 作者很多时要评估单一有序 SQL 来源、索引扫描和候选读取成本。预算不足不得推进到未知队首之后。
- L2/L3、榜单窗口精度、签名 URL 撤销能力沿 V2.1 的开放决策处理。
