# 购买入口与中奖退款实施契约

2026-11-18；本轮在既有未提交工作树继续，不修改历史证据，不提交或推送。规则来源是本轮用户确认；本说明取代追加 PRD 中旧的关注授权、禁止购买与开奖并存、中奖自动退款行为。

## 购买、下载、退款

- POST purchase 的身份仍来自可信登录上下文；所有登录用户可购买，不查询关注图、素材预览或分享授权。未登录 401，黑名单拒绝，活动未开放/未开始/结束、售罄、中奖已拥有明确返回业务码。
- 账号/clientKey 重放继续返回首次请求；同素材不同 clientKey 不制造第二份订单。同账号素材限购跨活动且退款不重置；只有中奖权益而无购买请求时返回 ALREADY_OWNED。MySQL UNIQUE(user_id,post_id) 最终兜底。
- clientKey 是不透明、精确匹配的字符串，Redis SHA-256 与 MySQL 的唯一键必须一致；新增迁移将请求列改为 utf8mb4_0900_bin（NO PAD），避免数据库默认的不区分大小写/重音排序规则把 Redis 已接受的不同键合并。既有行内容不变，历史已合并的请求不会被拆分或重新创建。
- 有效 PURCHASE 下载权益只对购买时绑定的版本绕过关注与分享密码/模式；省略 versionId 时解析到购买版本，不随作者默认版本升级。其他版本继续走既有授权，素材下架后禁止签发新链接。既有签名 URL 到期前可用的边界保持不变。
- 发奖与落单持有同一 account_material_decision_locks 行。发奖保留 PAID，插入中奖权益、通知及权益缓存同步任务；禁止新自动退款。
- 新入口 POST /api/orders/{id}/giveaway-refund-requests。只有订单本人、PAID 且持有同素材有效中奖权益才能申请；同原因重复申请返回同一申请，重复成功审批返回原结果。其他原因已申请/已成功退款不改写原因。商家审批沿用现有接口。强制退款始终记 BUYER_FORCED。
- GIVEAWAY_REFUND 成功保留中奖权益并计入 PURCHASE；BUYER_REQUESTED/BUYER_FORCED 成功不计入。历史 GIVEAWAY_AUTO 保留读取与资格兼容。

## Redis 与 MySQL 的职责

- 入口只执行 Redis，不在成功返回前做 MySQL INSERT、权限查询或 MQ send。正常成功立即返回 PROCESSING；查询接口可读取 Redis 中尚未落库的本人请求。
- 预热活动 ID、素材/商家、冻结价格/版本、窗口、库存及账号限购/中奖/黑名单状态。未就绪或损坏 fail closed，不自动回源放行。
- 跨活动同素材限购与账号/clientKey 需要跨活动原子检查，采用新的统一 hash tag 命名空间；当前单实例拓扑不变。此方案是单 Redis slot，不能宣称已完成集群分片容量扩展。旧命名空间和旧 Stream 保留用于迁移/审计。
- 同一 Lua 中验证键类型与资格、扣预占、记录请求和 XADD。禁止把 Lua 的隔离性误称为任意运行时错误都会自动回滚；类型/数据校验在写前完成，失败显式暂停和对账。
- Stream 消费组读取有固定批量上限；提交 MySQL 请求与待发送记录后才能 XACK。崩溃前未 ACK 的消息通过 pending 接管重放，reservationId/请求字段不变，唯一约束保证重复消费不重复持久化。
- MQ 待发记录使用短领取事务、租约与 token；send 位于事务外，仅真实 SEND_OK 后条件确认。超时/非成功 ACK/过期 token 不可确认成功；消费者仍通过请求状态、回执与账号素材锁幂等落单。
- V23 起，ACK 确认时间与 SENT 同事务写入 `material_sale_dispatch.sent_at_ms`，发送确认不再更新消费者持锁的购买请求行。请求表旧 `mq_sent_at_ms` 保留历史值，新投递监控读取 dispatch，不能因旧列为空判为未发送。
- MySQL 落单最终复核黑名单、账号已拥有、活动及窗口、帖子下架、库存、冻结素材版本。订单、库存、权益、请求终态、消费回执同事务；拒单缓存释放可重试且只能归还一次。

## 控制状态同步与恢复

- 拉黑/解封、关闭/下架、权益变更、退款库存变更，在业务事务内记录持久化缓存同步任务。Redis 应用有 revision/generation 校验，旧任务不能覆盖新状态，失败保留任务重试。
- 下架与关闭活动同 MySQL 事务，最终结算不依赖缓存的及时性。Redis 控制变更未确认时不能假称缓存已同步；后台最终权限复核始终生效。
- Redis 连接异常、就绪标识缺失、运行实例变化、损坏标识触发暂停。数据库恢复状态/租约隔离桥接、落单、退款和发奖；恢复过程无长数据库事务。
- Lua 每次对照 Redis 实际 run_id 与本次恢复发布的实例标识；即使 AOF 恢复了 ready=1，进程重启也会立即拒绝受理，不能等下一次后台扫描才暂停。恢复发布同样校验实例，避免重建期间再次重启后错误开放。
- 恢复先暂停入口，接管并持久化尚存的 Stream/pending，随后依据 MySQL 的订单、待结算预占、中奖权益、黑名单和活动状态重建库存及防重，恢复缓存后再开放。旧恢复执行者不能覆盖新 generation。
- 当前 Docker Redis 为 AOF + noeviction。AOF everysec 不等于零 RPO；若 Redis 内存与 AOF/备份全部丢失，尚未桥接的预占不能凭 MySQL凭空还原。必须暂停并恢复权威状态，未能核实的旧 reservation 视为未知，客户端可用原 clientKey 重试；不返回伪造支付成功，也不把未知当成已经确认的业务拒绝。已入 MySQL 的请求、订单和回执可恢复且不能重复成交。
- 切换版本前必须停止全部旧版购买入口实例。新桥接器带持久化游标读取旧 Stream 的孤立 PROCESSING 记录；保留原键与 Stream，不允许新旧入口同时在两个库存命名空间售卖。上线前等待 runtime=RUNNING 且新控制键 ready=1；普通 readiness 本身不能代替购买缓存的就绪检查。
- 真实历史数据存在跨活动复用 clientKey 的孤立旧预占。导入时若账号/clientKey 已有另一条持久化请求，以首次持久化请求为准，在 V22 审计表保留旧 reservationId、原 Stream ID、原请求及首次请求快照；审计与导入游标同事务，不再生成第二条请求、待发送记录或订单。旧 reservationId 的本人查询关联首次请求，其他身份仍拒绝；原旧 Redis 数据不改写。V22 规则仅处理旧命名空间；新 Stream 身份冲突仍不得当作幂等成功。2026-11-19 经用户明确授权，新增持久化隔离、可信预占释放及恢复阻断协议，详见 `docs/commerce-stream-batch.md`，不改写原 payload 或首次请求。

## 初始运行参数

- Stream 单批最多 200，pending 最小空闲 30000ms 才接管；Redis 重建时在数据库恢复租约保护下使用 idle=0 接管保留消息。
- MQ dispatch 租约 30000ms，单次客户端发送超时 10000ms；失败退避为 `min(60000,250*2^min(attempts-1,8))` 毫秒，首次失败 250ms；次数累计、不设静默丢弃上限。确认与重试均检查 SENDING、token 和数据库时间下有效租约。
- 恢复租约 120000ms，以数据库时间校验，每一页读取前续租。过期者不能安装或发布缓存。Redis 状态损坏保留隔离副本，不当作正常库存耗尽。
- 后台 Stream/同步与 MQ 发送使用两个独立调度任务；本地压测沿用既有 50ms 扫描和 20 个 MQ 消费线程，不改变 HTTP、JDBC、Redis 超时或既有线程池参数。

## 验证与性能口径

先执行可编译行为 RED，真实 MySQL/Redis 验证事务、Stream pending 接管、提交前/后崩溃、重复消费、释放、缓存同步与全量丢失恢复；真实 RocketMQ 验证提交和 ACK 故障窗口。测试夹具不代替生产 scanner、outbox sender 或消费者。

相关回归与 8–20 单 smoke 通过后，才用原 5000 个测试账号、新独立活动、库存 100、Loops=1、RampSec=1、WarmupThreads=0、超时各 30000ms、BarrierGroupSize=5000/120000ms 复测。ready=5000、timedOut=false、sampler 启动跨度≤5000ms 才是有效同步跑次。按成功受理/SOLD_OUT 分组报告 SQL 次数、应用内/HTTP 耗时、最终订单/库存/权益/回执；无效跑次不宣称性能提高。
