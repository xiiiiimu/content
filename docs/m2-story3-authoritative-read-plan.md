## 推荐的下一个最小 Story

**生产主库候选来源 + 权威关系/状态判定 + 内部读取组合服务**。复用 FeedMerger，不做 HTTP、登录、签名令牌、关注写接口、MQ 消费/分发或 Redis 自动启用。主库是配置明确的 writer/master DataSource，不能静默落到只读副本或读状态缓存。

建议先以一个完整主库来源覆盖保留窗口内的所有已发布候选，再按读者当前权威关系过滤。该基础路径覆盖 PUSH/PULL 以及不可变旧模式/epoch 的帖子，不以作者当前模式筛掉历史，不依赖 Redis 到达或 M3 扇出完成。RedisCandidateSource 继续作为可复用组件，但不进入此生产组合，直到 M3 有覆盖/恢复证明；不能把缓存 miss 当作该读者没有帖子。

### 候选及真实工作预算

建议来源先按固定窗口与快照，从主库 `posts` 的已发布有序索引进行单一 keyset 原始候选扫描；单次至多 32，随后由权威校验拒绝未关注/越界历史/下架项。这里的“原始”候选可能属于其他作者，始终只存在于服务内部，未授权项不能进入返回 items。这样不会将大量关系过滤藏在返回 LIMIT 之前，能把实际提交给内核的每个元组纳入 scanned/checks。

这是可验证完整性的最小基线，低关注密度会带来更多空 UNKNOWN；不宣称它满足生产吞吐。若容量验收不接受，应另行提出按关系过滤的查询方案及物理扫描预算，不静默改为无界 per-author fan-out 或无界 JOIN 后 LIMIT。

- 输入：服务内部可信 readerId、固定 snapshotTime、固定窗口下界及 G/C；时间窗与排他边界绑定整条续读链。保留窗口的业务值须在 RED 前冻结，不擅自写入 7 天等新默认。
- 来源 SQL：status=PUBLISHED、窗口下界<=published_at_ms<=snapshotTime、二元组严格小于安全上界，二元组 DESC、固定 LIMIT；禁止 OFFSET。考虑新增 `(status,published_at_ms DESC,id DESC)` 索引，必须先用真实执行计划证明需要与效果；如需变更只能新增 Flyway V4，保留 V1–V3。
- 每次来源回调只允许一次有界候选 SQL；每个权威回调至多一次按 post PK 查询并关联当前关系/白名单的 SQL。关系/白名单用现有复合主键或有证明的新索引，不能加载整个作者集合或历史集合到应用层。
- 图版本在请求前后各检查一次，单独计入服务预算。按现有上限，计划最坏 64+256+2=322 条 SQL 调用，不含连接健康检查；不允许回调内部自动重试或补查逃逸计数。参数、空读、页尾确认及失败调用同样计入。
- SQL 返回 LIMIT 不代表物理 rows examined 上限。需记录 EXPLAIN ANALYZE/实际 examined rows，验证有序索引范围扫描、无全表排序/全量装载；对稀疏关注和大数据夹具明确成本。数据库语句执行上限、网络超时、连接池、独立执行器及有限队列/拒绝策略在 RED 前冻结，并实测超时后资源释放。Future 取消不是服务器已停止的证明。

### 权威判定与读者上下文

每项读取帖子真实 canonical 元组、status、author_id、publish_seq，以及当前关系状态、epoch、cutoff 和该 epoch 的白名单命中。只有：

`post.status=PUBLISHED AND 当前仍关注 AND (post.publish_seq > 当前 follow_cutoff_seq OR 当前 follow_epoch 的 follow_history 命中 post.id)`

才可返回。历史名额已物化，不按当前前 N 条重新计算、不补位；同一发布元组不得被 Redis 更改。canonical 不符是错误，不按错误元组继续推进。帖子不存在为不可见；数据库查询失败是不可用，不是不可见/耗尽。

内部 reader 上下文由调用者提供，不能宣称完成 HTTP 身份认证；数据访问参数绑定 readerId，任何外来候选均须按同一读者检查。服务前后读取最新 graph version；输入版本不符或期间版本变化时，不发布部分结果/新 continuation，而返回内部 stale 结果，留给后续令牌/API Story 映射 CURSOR_STALE。避免一个长 RR 事务将最终版本校验固定在旧快照。下架提交后发起的新请求必须读到主库新状态；提交前已通过检查的在途响应仍沿 ADR-004 单列边界。

### 与 M3 的依赖及夹具退出

- M0 已有表，M1 已持久化 publish_seq；足以编写真实的生产读取 DAO 和判定服务。
- M2 读取侧代码契约可以用事务性夹具准备合法关注事实来验收，不要求先实现全部 M3，避免阶段循环依赖。夹具只替代事实准备，不能替代生产读取/判定逻辑；M3 未完成前不能宣称关注写入、异步分发和恢复的生产链路已可用。
- M3 仍负责在作者模式行锁下原子建立 epoch/cutoff/固定历史集合及图版本；本 Story 只读这些事实，绝不根据现有帖子临时猜 cutoff、创建关系或扩大历史。没有可信写入协议，不能宣称已有可用的生产关注链路。
- 测试可以事务性种入合法关系事实，但测试必须调用 `src/main` 的真实 MyBatis DAO、权威判定器及组合服务，而不是 test lambda 替代目标逻辑。独立 SQL oracle、数据准备、屏障仍留在 src/test。
- 发布 JAR/默认 Spring 组合不能引用测试来源、任意 SQL predicate、恒真权威校验器或 fixture profile。缺依赖、未初始化/不可信图版本、缺失需校验的序号等情况应失败关闭，不能回退 allow-all；具体错误与初始化规则在 RED 前冻结。
- Redis 分发/恢复、旧模式历史迁移和关注生命周期不在本 Story 实现；将来引入混合来源时，需证明相同边界与窗口覆盖，无法证明则保持完整主库路径或要求刷新。

## 实施前仍需冻结的定义

现有 ADR 定义“当前仍关注”，但仓库未给出 follows.status 的正式枚举字面值；也没有固定本读取路径的保留窗口、未初始化图版本的生产初始化契约及语句/总请求资源阈值。这些是下一 Story 的输入定义，必须核对 V2.1/另行确认后记录，再写 RED；本计划不自行将 ACTIVE、FOLLOWING 或任意天数当成已冻结协议。不影响 PR #4 已限定为接口/夹具的验收结论。
