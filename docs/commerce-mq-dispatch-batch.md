# MQ 待发送批处理：审计与实施约束

2026-11-19。在既有未提交工作树继续，不提交、推送、合并；桥接固定20，消费者20线程，HTTP与发送超时保持不变。

## 已核对的基线

- MySQL 8.4.13；原领取使用 `FOR UPDATE SKIP LOCKED`，但以 PENDING到期 OR SENDING过期共同筛选，再按 available_at_ms/reservation_id 排序。当前索引为(state,available_at_ms,lease_until_ms)，现有数据下 EXPLAIN 为range并包含Using filesort。空闲表执行计划不能代表3000条积压下的实际CPU成本。
- 每次领取：runtime FOR SHARE、未知范围HOLD检查、next FOR UPDATE、claim UPDATE、dispatch SELECT，共5条SQL、一次事务。UPDATE递增attempts/token并设置数据库时间+30000ms租约。
- 事务外发送：按reservationId查询购买请求，构造PurchaseSettle消息，key为reservationId，显式10000ms发送超时，客户端内部失败重试0。只有SEND_OK为成功ACK。
- 成功确认：独立事务，一条dispatch UPDATE，同时写SENT/sent_at_ms，条件为reservationId、SENDING、token、有效租约。不得恢复对购买请求行mq_sent_at_ms的更新。
- 失败：独立事务，一条dispatch UPDATE，同样检查状态/token/租约；回PENDING，退避min(60000,250*2^min(attempts-1,8))ms。
- 原协议是attempts累计、不设静默丢弃上限，只有PENDING/SENDING/SENT；本轮不擅自新增DEAD或丢弃策略。用户提及的原尝试上限按此既有契约理解。
- 两个调度线程分别处理桥接/缓存同步与发送；发送任务逐条完成领取、send、确认，循环上限20，循环结束才等待50ms。它不是20个发送执行者。

历史20档：发送领取P50/P95=97/265ms，确认53/169ms，实际MQ send10/33ms。JFR SQL区间包含数据库执行、锁等待、网络和驱动开销，无法直接分离纯服务器CPU时间；MySQL锁等待为离散采样，不能把一次SQL的完整elapsed都当作锁等待。尚无证据支持扩大连接池。

## 批事务和并发约束

候选使用MySQL8的FOR UPDATE SKIP LOCKED并分开扫描过期SENDING与到期PENDING，保留过期任务的领取份额，避免available_at_ms为0的新任务长期压过过期任务。拟新增适配这两条有序扫描的索引，通过新增Flyway迁移实施，不修改V20/V23。

一批共用一次领取事务，逐条分配递增token、计一次尝试；领取提交前不发送。发送在事务外且队列/线程/数据库连接有上限。成功和失败分开批量持久化，逐项核对ID/state/token/租约，部分条件未命中不能把整批标为成功。确认事务失败保留可接管记录，不能伪造ACK落库成功。事件key及持久化payload重投不变；请求表不承担发送确认写入。

## 用户确认的租约容量边界

现有租约30秒、单次MQ超时10秒。实际批领20、并发1的最坏发送时间为200秒，并发4也可能达到50秒，均超出租约，不能以历史send P95很小替代故障边界证明。

用户确认方案1：保持原30秒租约，不新增续租。上限配置20，初始实际最多并发1领取2条、并发4领取8条，并受当前剩余执行容量限制。领取事务、队列等待、MQ发送和确认全部纳入租约预算。每次开始发送前检查剩余租约，不能覆盖10000ms发送及5000ms确认余量时停止该任务发送，保留SENDING等待原协议接管；不得提前冒充失败或成功。发送完成后的确认仍由数据库时间、状态和token最终决定。

5秒余量不是忽略超时的保证：必须实测确认耗时并核对客户端调用上界，发生预算违例如实记录、停止扩大负载，不能续租或放宽超时。客户端内部失败重试保持0，元数据/网络内部步骤是否受send总超时严格覆盖需要结合客户端代码核对；未能证明时列出边界。实验B/C标注为“上限20、实际按容量领取”，不宣称实际20条。
